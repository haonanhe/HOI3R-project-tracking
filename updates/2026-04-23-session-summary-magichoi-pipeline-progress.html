Key discoveries

FIX MagicHOI only_3d uses Zero123, NOT depths

Stage-1 SDF non-convergence is not caused by zero-stub depth maps. only_3d takes do_3d_guidance_only=True, which routes through zero123_guidance.py:99/324 and skips both visibility_binarys (depth) and visibility_colors (RGB recon). Depths are only consumed in stage-2 align_corres.py via --query_depth_f. Replacing zero stubs with Metric3D depths won't unblock model.obj. See project_magichoi_only3d_zero123_finding.md.

FIX Aliyun pytorch-wheels mirror works

pytorch.org wheel download from debug container stalls at ~80%; Tsinghua Tuna returns 404; mirrors.aliyun.com/pytorch-wheels/cu118/... works at 26 MB/s for the 2.15 GB torch 2.0.1+cu118 wheel (84 s total). Verified with zipfile.testzip() — 10,092 files. Saved as feedback_pytorch_wheel_aliyun_mirror.md.

FIX v13 patches: makedirs + None-safety

Two inline patches in scripts/acp/acp_magichoi_diag_startup.sh let MagicHOI's stage-1 export write camera.json even when SDF is degenerate: run.py::export_cond_cam now os.makedirs(os.path.dirname(cam_f), exist_ok=True), and threestudio/models/mesh.py::remove_outlier returns self when max_comp is None. The downstream amin() on empty v_pos still raises IndexError but run.py's `|| true` swallows it; ACP exit 0.

FINDING Truncated wheels look intact at the start

Prior session's torch wheel scp left 2,251,915,264 bytes (vs correct 2,267,322,772). File starts with PK\x04\x03 (valid local header) so it looks like a zip, but unzip -t says 'End-of-central-directory signature not found'. pip install rejects with 'Wheel ... is invalid'. Always verify wheels with zipfile.testzip() before pip install.

FINDING droid.pth is the small fnet-only variant

User-supplied droid.pth is 16,061,701 bytes (~16 MB, 4M params), much smaller than the typical full DROID-SLAM checkpoint (~287 MB). torch.load returns OrderedDict with module.fnet.* keys — appears to be the recurrent-backbone subset HaWoR's hawor_slam.py needs, not the full DROID.
